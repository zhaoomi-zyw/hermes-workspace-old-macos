### ⛔ 两个只在四条件回测里暴露的引擎缺陷（基础引擎 v4 也有，改前先读）
1. **停牌行污染滚动指标**：腾讯日K 只在真实交易日有行，baostock 日线却有 `tradestatus=0` 的停牌行（成交量 NaN、收盘沿用前值）。用前缀和/rolling 时必须先建**真实交易日紧凑索引**，否则 MA/DSA 系统性失真（本例 600 抽样点 4 点不一致）。
2. **挂单跨午休成交**：基础引擎把午休按「交易时钟压缩」⇒ 11:30 的信号可在 **13:00 成交**（真实券商 15 分钟有效期不跨午休）。修法：挂单记 `session`(am/pm)，成交前比对 bar 时段，不一致即失效。**修完后旧结果必须归档 `v1_superseded/` + README 标注作废**。
3. 另外：`price > MA5` 在 price 恰好等于 MA5 时存在 **1e-13 浮点刀锋**（前缀和 vs `sum(list)` 求和顺序不同）→ 600 抽样点中 1 点 DSA 差 15 分，属数值噪声，如实记录即可。

### ⛔ DSA 实现唯一来源（2026-09-15 写错权重的教训）
**绝不在临时脚本里重写 `dsa_score`。** 本次重写版权重记错（写成满分 100，实际 **115** = 15+10+10+10+15+15+15+10+15），同一只股两轮算出赔率 **1.70 vs 1.93**、信号数 59 vs 107 —— 结果不可比，差点把错的当结论报给用户。
**正确做法**：从生产脚本**抽函数体 exec 进命名空间**（不 import 整模块，避免触发其 `main()`）：
```python
import re
src = open(os.path.expanduser("~/.hermes/profiles/main/scripts/lowbuy-watch.py"), encoding="utf-8").read()
ns = {}
for fn in ["sma", "dsa_score", "grade"]:      # dsa_score 与 lowbuy/signal_daily/dsa_scores v1 对齐
    m = re.search(rf'^def {fn}\(.*?(?=^def |\Z)', src, re.M | re.S)
    if m: exec(m.group(0), ns)
sma, dsa_score = ns["sma"], ns["dsa_score"]
```
**自检（必做）**：`dsa_score(range(1,101), range(2,102), range(0,100), [1]*100)` 必须 ≈ **109.8 → S 级**（验证满分 115 与分级阈值 S≥90/A≥80/B≥65/C≥50 对得上）。自检值不对 = 函数没取对或权重记错，**立刻停手**。

**核心铁律(写给未来的自己)**:
- **回测收益 ≠ 实盘可得收益**。判断策略必须叠加"执行可行性"层(滑点/追价/涨停买不到/信号确认时点)。任何"纸面更好"的策略, 先问"实盘能在那个价格成交吗"。

- **⛔ 报告的判据必须来自 skill, 不得自行发明 (2026-09-15 用户追问「什么缺陷」暴露)**：skill 里已有的**数据裁决结论**是报告的上位约束, 但 **cron/会话报告的 agent 常常只读到「案例教训」那半段, 就自行发明一条"缺陷/隐患"写进推送**。**自检判据**: 报告里出现「缺陷 / 隐患 / 留意 / 需警惕」字样时, **必须能指向 skill 中一条【已启用规则】或【经数据支持的结论】**; 指不到就删掉该句。
  - **反例(本案例)**: 2026-09-15 收盘前检查写「MA5(35.30)<MA10(36.85) 短期仍空头排列, **与9/10那笔同一缺陷, 留意**」—— 而 skill 第⑥条**早已写明该假设被 1217 样本否决**(MA5<MA10 的信号反而略好)。**是 skill 有正确记录、而报告 agent 没读到否决结论** → 结论: **发现报告与 skill 结论矛盾时, 先怀疑报告 agent 漏读了否决条款, 而不是怀疑结论错了**。

**③ 引擎坑二：买入限价取整到分 → 一半信号被误判「价格越界」不成交**。`L=round(price,2)` 后与**未取整**的 bar close 比 `bc <= L`: 21.784 的收盘 vs 21.78 的限价直接判越界。修法: **买入限价用 `ceil`**(`np.ceil(price*100)/100`; 买单限价是上限, 抬不到 1 分钱), 再用 `bc <= L` 判成交。另: 「阻挡原因」上报要取**最小手数**那条而非法循环第一条, 否则永远显示最大手数触发的那个原因。

**④ 盘中 high/low 先后顺序(必读, 极易白做一遍)**: 保护线**单调不降** ⇒ 触发条件「低点 ≤ 线」本身**与顺序无关**(被抬高的线只会让触发更容易), 两条假设路径的**触发日完全相同**, 差异只在成交价归属。**因此若把 O-L-H-C 实现成「先用当日高点抬高保护线、再用抬高后的线判当日低点」, 两条路径会退化成一模一样的结果**(本次先跑出两份完全相同的数字才发现)。严格 O-L-H-C 必须: **当日低点只用「当根之前已确立的线」判定, 不得被当根自身高点抬高的线触发**。默认取悲观序(先 high 更新线 → 再 low 判触发)并把顺序敏感性单列为一项报告。
**2026-09-15 独立审阅补齐的 3 条点位顺序要求(缺任一条即建模错)**: ①**开盘价必须最先对「当根之前的线」判定** —— 若当根开盘已低于旧线, 必须按**开盘价**成交, 不得先看当根 high 抬线、再用抬高后的线去解释一个更早的价格(那是用未来信息解释过去); ②除 low 外还必须判 **close**: O-L-H-C 路径要在 high 抬线**之后**再判「收盘跌破新线」, 否则整类触发被漏掉; ③**触发事件与可执行价格必须分离** —— 触发归因到哪条线(硬止损/盈利保护)与实际按哪个价成交(触发点价、受跌停价约束、计滑点)是两件事, 分开记录才能审计, 且**不得按虚构的保护线保证成交**。

## ★★ 回测引擎正确性审查清单 (2026-09-15 独立审阅暴露 12 类缺陷 — 新引擎先过这张表) ★★
> 用户会**独立审阅引擎源码**并**逐条**指出缺陷, 且**不止一轮**（本任务被连续打回两轮: v2→v3 12 处, v3→v4 3 处更深的问题）。完整缺陷清单+修法+复现命令: `references/backtest-engine-correctness-review-2026-09.md`。**任何新写的回测引擎, 交付前先对着这 11 类自查** —— 它们都不报错、只把数字搞错。
> ⚠️ **审阅会追问到「语义层」而不止「代码层」** —— 第二轮的三条都不是 bug 而是**建模语义错**: T+1 到底阻什么、开盘那一瞬间能知道什么、状态字段代表什么。写完引擎先自问一遍这三问。

1. **统计累加必须只发生在真实成交**。最隐蔽: `_recommend` 用 `_try_buy` 当**探测**(判断能不能买得起), 而 `_try_buy` 里 `res.fee_total += ...` ⇒ ①每笔真实成交被加 **2 次** ②**没成交的试探也被计费**。修法: 拆出**纯计算的 `_size()`**(不改任何状态、不碰 `res`), 探测只调它; 只有成交路径才 `accrue()`。验收就是上面的 ⑪ 费用守恒。
2. **限价单语义**: 严格执行价必须 **= 限价 L**; 滑点作为**独立成本项**另计, 不得把成交价抬到 L 之上(否则「限价」形同虚设, 且可能落到 ATR 允许区间之外)。
3. **信号根不能给自己成交**(经典未来函数): 信号在 K 线 b 收盘形成 ⇒ 最早只能在 **b 之后**的 K 线成交。判定可执行性要用 K 线的**窗口起点**(不是收盘时刻), 否则 5 分钟粒度下「延迟 0」与「延迟 5 分钟」会退化成同一根 K 线。
4. **限价单有效期要真的实现**: `ORDER_VALID_MIN` 定义了却不用 = 常量摆设。正确: `placed_clk` / `expires_clk = min(placed+15分钟, 14:45)`, 到期未成交按**券商撤单**释放、**不带入翌日**。延迟按**交易时钟**计(11:30-13:00 午休压缩, 不额外消耗延迟分钟数)。
5. **估值绝不能回退到「当日最终收盘」** —— 那是未来信息。无分钟数据时回退**上一完整交易日收盘**或**最后已观测价**。
6. **单笔风险必须含买入费用**: `(fill-hard)×qty + 卖出费用` **漏了 buy_fee**, 会系统性低估风险。
7. **场景间不得共享可变状态**: `last_close` 这类缓存若挂在共享数据容器上, 场景 A 污染场景 B。移进 **Simulator 实例**。同理冷却重置判定要**用各场景自身参数**(`atr_k`/`vol_ratio_max`), 不硬编码常量; 且**缺失/停牌数据不算「条件失效」**。

### 第二轮复核 (v3 → v4) — 三条建模语义错, 比代码 bug 更隐蔽
8. **T+1 只阻止「成交」, 绝不阻止「触发」** ⛔⛔ 本次最严重。v3 用 `if p.get("entry_today"): continue` **跳过建仓当整天的 H/保护/止损更新** —— 等于「当日买的不许看行情」, 直接违反 T+1 语义。**正确**: 买入后**照常**按有序价格事件更新 H、开保护、判触发; 当日 `sellable_qty == 0` 时**只阻成交不阻事件** → `fire_exit()` 落 pending, **次交易日首个可成交时点退出, 反弹不撤销**。**验收必须用合成测试**(见 ⑲), 因为主回测里这种情况只有 2 笔(T1_DEFERRED_EXIT), 靠市场数据撞不出来。
9. **开盘成交不得用「当根 bar 最终的 low / volume」判定 — 那是未来信息** ⛔⛔ 用整根 bar 的结果去解释 bar 开头就已经发生的那个成交 = 未来函数。**正确(careful, reproducible)**:
   - 候选成交价 = **下一根 bar 的 `open`**; `fill = open`;
   - 量比重验**只用「开盘之前已完成 bar」的累计量同刻比**(即前一根 bar 结束时刻的同刻比; `13:00` 复用 `11:30` 的比值, 因为午休区间累计量恒等);
   - 价位/区间检验只用**当前 open**: 要求 `open*(1+滑点) <= 限价` **且**仍落在 ATR 允许区间内; 不满足 → **本根不成交, 继续等下一个 open 直到真实到期**(不是撤单);
   - 成交时刻定义为 `该 bar 的 open 时刻 = 前一根 bar 的结束时刻`(当日首根 09:30; 午休后首根 13:00) —— 用这个时钟判 `[placed+delay, min(placed+15,14:45)]` 与「是否落在允许买入时段」;
   - **同一根 bar 内的次序**: **先在 open 成交, 再处理该 bar 之后的 H/L/C 退出事件** —— 否则建仓当根的 T+1 触发事件永远记不上(与 8 联动);
   - **整根零量 bar** 若用于过滤, 必须作为**「无法交易的数据缺口」独立披露**(`data_gap_zero_volume_bar_no_fill`), 不能混进正常的成交判定理由里。
10. **字段不许混同**: `限价 L` / `实际成交价(=open)` / `含费含滑点成本价 C` 必须**分成三个字段**。v3 把「成交价」写成限价, 又被追问「买价含费字段不要混同成交价」。审计脚本要能分别取用。
11. **账本要留可精确对账的现金流出字段**: 只存「成本价 C」时, `C*qty` 与真实现金流出会因 `round_cost`(3 位)产生残差, 本次现金对账残差 0.30 元 → 加 `cash_out = amount + buy_fee + slip` 后对账残差降到 **0.0034 元**。**验收**: 逐笔 `-cash_out + proceeds_net` 重放 == 账本期末现金。

**另一类必加的门控(本次缺)**: 停牌日不交易、**零成交量 K 线不成交**、一字涨停不买、一字跌停不卖、成交价受涨跌停价约束(主板 ±10%, 用 `preclose` 推)。

### ⚠️ 归因纪律: 没有消融就不许说「是 X 导致亏损」(本次两次自我打脸)
1. **跨消融比较「期末权益」不是同口径比较** —— 期末权益会被**未平仓头寸污染**。本次「关闭盈利保护」消融看起来把 -17.18% 变成 +34.75%, 一看明细: 其**已实现盈亏 -2,759 与基准 -2,912 几乎相同**, 差额几乎全部来自期末两笔未平仓浮盈(亨通光电 +420%、赤峰黄金 +115%)。**修法: 消融表必须同时给「已实现盈亏」与「未平仓浮盈」两列**, 否则结论完全反了。
2. **退出线宽度与仓位大小通过风险预算强耦合** —— 把止损放宽到 -99% 想消融「取消退出」, 结果 2% 损失预算下**一手都买不起(0 笔)**。「只改退出、不动仓位」的消融**在本策略里不存在**, 要如实说不可行, 而不是报一个 0 笔的假结果当结论。
3. **基准口径不许混**: 12 只「各自满仓的独立账户」的平均收益**不是任何可行组合的收益**, 不得与主组合或等权组合横比。真要给等权基准, **必须受 100 股整手与现金约束** —— 本次 13,822.47 元等额分 12 份(每份 1,151.87 元)后**只投得出 7.96% 的现金**(多数标的买不起一手), 组合收益 +5.79% vs 10 万口径 +116.68%。这本身就是「小账户无法真正等权持有 12 只」的实证。
4. **收益集中度 = 单笔最大盈利 / 已平仓净利润总和**, 取值可为负、可 >100%(>100% 表示最大一笔盈利超过全部净利润之和)。**说「某笔超过全部净利润」前先核对那个百分比是否真 >100%** —— 本次口头把 71.41% 说成「超过全部净利润」, 被用户当场指出矛盾。

## akshare data source — CRITICAL quirks (learned the hard way)
1. **Eastmoney source (`stock_zh_a_hist`) breaks on large requests.** A 5-year single request reliably fails with `Connection aborted / RemoteDisconnected`. FIX: **shard by year** and concat.

## Backtest engine must encode A-share rules
- **T+1**: can't sell shares bought same day.
- **涨跌停**: ±10% (主板). Limit-up → can't buy; limit-down → can't sell. Judge using `prev_close` (shifted close).

  1. **10日高点含当日 = 未来函数**: `max(hi[-10:])` ❌ → `max(hi[-11:-1])` ✅（等价 `.shift(1)`）。**任何 rolling max/min 都要问「含不含当日」。**

- **整手**: buy in lots of 100 shares.

## Strategy pitfalls (all hit and fixed in this session)
1. **Future-function bug (the big one): support/resistance must use yesterday's value.** If you compute `resistance = high.rolling(N).max()` (including today), then today's close can never exceed today's resistance → **breakout signals permanently return 0**, silently. FIX: `.shift(1)` the rolling support/resistance so today's signal is judged against yesterday's level. This single bug flipped 工业富联 from -17% to +167%.
2. **Entry period ≠ exit period.** Using the same 20-bar window for both entry (支撑/压力) and exit (MA20) caused average holding = 1 day — the strategy chopped itself out on every wiggle. FIX: exit on a **longer trend MA (MA60)** + **trailing stop** + **profit lock** (only enable trend-exit once profit > `profit_lock`, e.g. +3%, so fresh entries aren't shaken out).
3. **Mobile/trailing stop**: track `peak_price` during the holding; exit when `close <= peak_price * (1 - trailing_stop)` (e.g. 5% from high).
4. **A-share data**: ~17 gaps >5 days over 5 years are normal (春节/国庆 holidays), not data errors. Zero NaN in OHLCV = clean.

## DSA → quant rule mapping (works well)
| DSA concept | Algorithm |
|---|---|
| 关键支撑位 | rolling N-day low, `.shift(1)` |
| 关键压力位 | rolling N-day high, `.shift(1)` |
| 缩量企稳买入 | price touches support (~1.02x) + volume < vol_ma × 0.8 → 半仓 |

## Tencent fqkline response-shape gotcha (2026-09-04 — burned 3 fetches)
When pulling daily K-lines for MA/支撑/压力 (any watch script), the URL form and the response KEY both matter:
- **Correct URL**: `web.ifzq.gtimg.cn/appstock/app/fqkline/get?param={code},day,,,{n},qfq` — the `day` field is followed by an EMPTY period field (`day,,,`), NOT a count. A 4-arg form like `param=sz000938,day,5,,qfq` (count in the 3rd slot) returns `{"code":0,"msg":"param error","data":[]}` silently — no exception, just empty rows.
- **Response key is `qfqday`, NOT `day`**: when the URL ends `,qfq`, the bars live under `j['data'][code]['qfqday']`; `.get('day')` returns None (KeyError/empty). Fetch defensively: `c.get('qfqday') or c.get('day')`. Each row = `[date, open, close, high, low, volume, ...]` — close is index 2, high 3, low 4.
- Realtime line (`qt.gtimg.cn`) fields f[3] price / f[33] high / f[34] low are the OTHER (unfq) endpoint; don't mix their indexes with fqkline row indexes.

## 基本面因子该不该加进 DSA? — 验证方法论 (2026-09-08, `references/fundamental-factor-validation-2026-09.md`)
Omi 问"DSA 该不该加基本面因子(ROE/毛利率等)" 后做的验证。核心是**方法论**不是结论:
- **季频因子不能做逐日 IC**(季度内因子值重复=伪独立观测, 虚假大样本高估显著性)。正确=**季度末对齐**: 每报告期因子值 × 该期后 3/5/20/60日收益, 一季一观测(11股×6季≈55点)。披露滞后用 报告期末+40自然日 近似收益起点。
- **小样本 IC 高到反常(+0.3~0.45) = 截面混淆信号, 不可信**: 学术单因子IC 0.05即算强; 11只自选全是强势股(样本有偏), 高ROE恰好走势强可能是选股偏好/行业属性, 非可交易规律。只能参考不能据此改策略。
- **周期错配是首要定性判断**: 基本面是季度慢变量, DSA 是日线快策略(2-3天~60天)——季度因子来不及变化, 预测短线在时间尺度上天然不匹配。真正契合短线的高频因子是**换手率/量能类**(每日有, 本质交易情绪)。
- 严谨下结论需扩池: 拉指数成分 50-100 只不同行业股票, 面板/分层检验(按因子值分档比高vs低组后续收益)才分离截面混淆。

## 不加基本面因子 (2026-09-08 决策确认)
Omi 问"DSA 该不该加基本面因子"(受小红书13因子多因子选股启发)。已做季度粒度 IC 验证(11自选×6季=55样本), 结果 ROE/存货周转/应收周转 3日IC 竟高达 +0.3~0.45 —— 但这是**小样本+截面混淆的假信号**(55点IC置信区间极宽; 工业富联这类高ROE大盘股整体强, IC反映"哪只自选这半年强"非"ROE高→短期涨"; 季度披露滞后40日是近似; 11只全是自选强势股样本有偏)。**结论: 不足以作为加因子依据, Omi 决定保持现有 DSA 纯技术策略不变。**

**周期错配是根本原因**: 基本面因子是季度慢变量, Omi 的 DSA 是日线快策略(2-3天~60天), 时间尺度不匹配。真正契合短线的高频因子是换手率/量能(情绪/活跃度), DSA 量能维度已在用。真严谨验证需扩股票池到 50-100 只不同行业做面板分层(11自选无法验证截面独立预测力), 工作量大且 Omi 倾向系统简洁, 暂不做。**除非 Omi 明确要求扩池, 不再主动建议加基本面因子。**

## Minute-frequency buy-point watchdog — persisted state machine (2026-09-02)
For a **same-day intraday buy-point monitor** that must run EVERY MINUTE (not 15-min), the 15-min entry-break-watch is too coarse (a pullback-then-confirm setup needs 1-min granularity). Build a state-machine watchdog persisted to a JSON state file so each 1-min tick resumes where the last left off. Recipe (`industrial-fulian-entry-watch-20260902.py`, verified 2026-09-02):
- **Persisted state** `~/.hermes/state/<name>.json`: `{state, samples[], fired{}, never_below_broken}`. `samples` keeps last ~20 ticks (`{t, price, cumvol, etfs{code:price}}`); `fired` is the strict-dedup map (each alert key fires once). Every tick: load → append sample → transition state → save (atomic via write-to-tmp + os.replace).
- **放量 (volume surge) via cumulative-volume deltas**: Tencent `f[6]` is CUMULATIVE volume (手). Compute per-tick delta `cumvol[t]-cumvol[t-1]`; surge iff current delta `>= mean(prior N valid positive deltas) * 1.3`. Requires ≥2 samples and a positive historical mean.
- **板块同步止跌 (sector confirmation)**: compare each ETF's current price vs its price 3-min ago (nearest sample with `t <= now-180`); require ≥2 of 3 ETFs not lower. This gates the final buy confirmation.
- **Two-path state machine**: (A) main path — price enters pullback zone (61.90-62.10) without ever breaking floor (61.60) → PULLBACK_HELD; then `>=confirm (62.25) AND surge AND sector-ok` → fire "回踩确认买点触发" once. (B) direct-break path — if it never pullback-held and `>=63.00` → fire "直接突破63不追" once, wait for retest zone, then re-break with surge+sector → fire "63元回踩确认买点触发" once. **失效**: `price <= floor` → fire "买点方案失效" once, no further buy alerts.
- **No-event = empty stdout** (watchdog: non-empty stdout is delivered verbatim to WeChat). Same event never re-fires (state `fired` map). Alert text must include 时间/现价/状态/量能倍数/板块确认 + "仅为条件提醒，不自动下单".
- **Trading-window gating in-script**: cron may fire every minute `* 9-11,13-14 2 9 *` but the script itself checks exact windows (930-1130, 1300-1459) and returns silently outside them. This keeps the cron simple while the script enforces precision.
- **Test-before-deploy**: syntax check + dry-run with an ISOLATED temp state file (never the real one); confirm empty stdout on a no-event tick and confirm the parse (fetch a real quote, print fields). Cron `run` triggers the next tick — a silent run confirms the watchdog won't false-fire on deploy.
- **Self-pause + annual-repeat mitigation (CRITICAL for date-anchored crons)**: a cron expression like `* 9-11,13-14 2 9 *` matches the 2nd of EVERY September (cron has no year field) — it will re-fire next year. Mitigate with TWO layers: (1) the script calls `hermes cron pause <job_id>` at the 14:59 close tick after marking state FINISHED (JOB_ID hardcoded in the script after the job is created); (2) a 15:00 one-shot cleanup `no_agent` cron (`0 15 2 9 *`, `deliver: local`) that pauses the main job AND itself. Script's self-pause must guard (only pause if a `cleanup_`-prefixed self-id) to avoid pausing the wrong job. Full transcript: `references/minute-buypoint-watchdog-2026-09.md`.

## Watchdog JSON persistence pitfalls (2026-09-03 — both crons crashed, shared root cause)
No-agent watchdogs that persist per-minute state to a JSON file (`~/.hermes/state/*.json`) hit a **dict-key type rot** bug. Two distinct manifestations, same family:
1. **int→str key rot on JSON round-trip**: `minute_key()` returns `int(timestamp)`, used as a dict key (`rec[mk] = {...}`). JSON object keys are ALWAYS strings, so after `json.dump` → `json.load`, keys come back as `"1788399960"` (str). The running dict then holds a MIX of int (this session, memory) and str (reloaded) keys. Any `sorted(rec.keys())` or `sorted(...)` over them throws `TypeError: '<' not supported between instances of 'int' and 'str'`. **Fix everywhere keys are sorted/compared**: wrap the sort key with a coercer `def _k(x): try: return int(x); except (TypeError,ValueError): return x`, then `sorted(keys, key=_k)`. Patch ALL sort sites — the same bug appeared in TWO functions (`consecutive_minutes_below` AND `main()`'s cleanup sort) inside one script; fixing one left the cron crashing 18 runs later.
2. **default-value type mismatch on load**: `load_state()` initialised `etf_samples: {}` (dict) but the runtime code did `st["etf_samples"].append(...)` (list) → `AttributeError: 'dict' object has no attribute 'append'` every run after the dict got persisted. **Fix**: make the default the correct type (`[]`) AND add a defensive normaliser on reload — `if not isinstance(st.get("etf_samples"), list): st["etf_samples"] = []` — so a corrupted/legacy state file self-heals instead of crashing forever.
**Recovery when a watchdog "failed N runs in a row"**: run the script directly to read the real traceback (cron message truncates it), fix code, `rm` the corrupt state file (forces clean re-init), then run once to confirm exit 0. Do NOT rely on the cron's one-line failure notice — it cuts the traceback before the failing line.

## Manual-run pollutes day-dedup state → cron goes silent (2026-09-08, breakout-watch)
Watchdogs dedupe "当日每只首次触发才推" via a per-day state file (`~/.hermes/state/<name>-YYYYMMDD.json` → `{"fired": {code:1}}`). **Running the script BY HAND during the trading day writes that same fired flag**, so the next real cron tick sees "already fired" and stays silent — a signal that SHOULD have pushed never reaches WeChat via the auto channel. Trap hit: 云南铜业 broke out at 09:52; agent hand-ran breakout-watch.py to see it fire (wrote sz000878 fired); 10:00 cron tick then correctly deduped to silence. Lesson: **never hand-run a deduped watchdog mid-session to "check" it** — it consumes the day's alert for any ticker that fires. To inspect instead, read the state file and the cron output dir, don't execute.

**Diagnosing "signal not received on WeChat"** — three possibilities, distinguished by files:
1. `~/.hermes/state/<name>-YYYYMMDD.json` mtime/content — was it marked fired, and when? A 10:00 mtime + `fired:{code:1}` after an agent hand-run = dedup consumed it (above).
2. `cron/output/<job_id>/YYYY-MM-DD_HH-MM-SS.md` — each tick leaves a log; `Status: silent (empty output)` = script ran, condition not met (or deduped); if it shows an alert but user got nothing = delivery problem, not trigger problem.
3. The cron's own `last_status` + `last_delivery_error` (cronjob list) — `ok` with no delivery_error but a legit alert in the output file = rare; check the iLink rate-limit cooldown errors which surface as `last_delivery_error` even when `last_status: ok` (微信限流, delivery dropped).

## Controlling the no_agent watchdog crons via cronjob tool (2026-09-08)
Reconfiguring these watchdog crons (buy-signal `9bb6c99d8d19`, breakout `bbac9e8f269e`, stop-loss `aa6316b0b52f`) has three traps when using the cronjob tool:
1. **`action=update` does NOT toggle `enabled`.** Passing `enabled:false` in an update returns the job still `enabled:true` (silently ignored). To disable a watchdog use **`action=pause`**; to re-enable use `action=resume`. Verify in the return that `state` flipped to `paused`/`scheduled`.
2. **`action=update` does NOT change `schedule` unless you pass the `schedule` param explicitly** on that same update call. A prompt-only update leaves the old cron expression in place. To change frequency (e.g. breakout `*/15`→`*/5`), pass `schedule` and confirm `schedule` in the returned job reflects it.
3. **Prompt edits and control edits are independent.** If you both rewrite the prompt AND pause/schedule, do them as separate calls (prompt via update; enable via pause/resume; schedule via update-with-schedule) and read the returned `prompt_preview`/`schedule`/`state` each time rather than assuming the batch applied.
4. **`action=update` CANNOT change a job's `model` (2026-09-10).** `model` is not in the update schema — passing it is silently ignored (no error). To change which model a cron runs on, edit `cron/jobs.json` directly: load JSON, set `j['model']='deepseek-v4-flash'`, write back. Verified: 晨间DSA `0d1bb1811d94` + 美股晨报 `e128a5971108` both had explicit `model: deepseek-v4-pro` (they override the global default, so changing `model.default` alone does NOT downgrade them). `model: null` on a job = inherit global default.
5. **The gateway CANNOT be restarted from inside the gateway process (2026-09-10).** Hermes blocks `hermes gateway restart`, and also blocks `nohup`/`disown`/`setsid` wrappers AND `launchctl kickstart` when issued via the terminal tool — the block message is "command or referenced script cannot restart, stop, or uninstall the gateway from inside the gateway process". There is no in-process workaround. **When a change needs a restart (e.g. `model.default` config edits, which are read at gateway startup), finish the config write, then TELL the user to run `hermes gateway restart` from a separate terminal.** Do not burn calls trying to force it. Profile gateways are launchd services: `ai.hermes.gateway-main` / `ai.hermes.gateway-pet-competitor` (`launchctl list | grep hermes` shows PID).
Also note: these watchdog scripts live under `~/.hermes/profiles/main/` which is NOT a git repo and NOT part of the Obsidian vault — cron config + scripts there have no version control; the vault only tracks `04-Trading/*.md` records.

## 模型名规范化 + "配置改了但没生效" 的验证法 (2026-09-11)

**现象**: 把 `model.default` / `auxiliary.vision.model` 设成 **`deepseek-flash`**(DeepSeek V4.1 Flash 的官方新名)后, config.yaml 确实写入了, gateway 也重启过, 但日志/会话里实际调用的仍是 **`deepseek-v4-flash`**。

**根因**: Hermes 有模型名规范化模块 `hermes_cli/model_normalize.py::_normalize_for_deepseek()`, 规则是:
- 已知 canonical(`deepseek-v4-pro` / `deepseek-v4-flash`)→ 原样通过
- 匹配正则 `^deepseek-v\d+([-.].+)?$` → 原样通过(覆盖 v5-* 与带日期变体)
- **其他一切 → `deepseek-v4-flash`**

`deepseek-flash` 是 "deepseek-" 后接字母, **不匹配**那个正则 → 落入"其他一切" → 被重写成 `deepseek-v4-flash`。**所以配置里写 `deepseek-flash` 是个无效名, 会被静默改写且不报错**。

**好消息(不必慌)**: DeepSeek 官方已把 `deepseek-v4-flash` **自动路由到 V4.1 Flash**, 所以能力/计费无差别 —— 写 `deepseek-flash` **没有**真的切错模型, 只是显示名不一致。

**给未来的自己**: ①切 DeepSeek 模型时**优先用 `deepseek-v4-*` 形式**(Hermes 认得), 别用 `deepseek-flash`; ②若日志里模型名"没变", **先去 `hermes_cli/model_normalize.py` 查是不是被规范化了**, 而不是以为重启没生效、反复让用户重启。

**验证"重启是否已加载新配置"**: 比对两个时间戳 —— `stat -f "%Sm" -t "%F %T" ~/.hermes/profiles/main/config.yaml` vs gateway 进程启动时间(`ps -o lstart -p $(launchctl list | awk '/ai.hermes.gateway-main/{print $1}')`)。进程启动**晚于** config 修改 = 已加载。⚠️ 但**长会话锁定其启动时的模型快照**(session id 带创建日期), 所以"当前会话模型没变"≠"配置没生效" —— 要看新会话/cron 的 `model=` 字段: `grep -o "session=[a-z0-9_]* model=[a-z0-9.-]*" logs/agent.log | sort -u`。

**板块内选股筛DSA** (给"某板块还有哪些高分"):
- **⚠️ 先刷数据再算分 (2026-09-08 踩坑)**: 用户问"更新DSA评分/哪些高分"时, `data/*.csv` 可能滞后数日(仅拉取时刷新, 不自动更新)——直接用本地CSV算分会给出旧收盘的分数/现价(如 9/4 价当 9/8 用)。**先跑 `.venv/bin/python fetch_data_hithink.py` 刷新 CSV 到最新交易日再算**, 否则报的是过期评分。

**⚠️ cron prompt 硬编码自选清单 (2026-09-10)**: 除脚本外，**4个报告类 cron 的 prompt 正文里也各写死了"自选N只"清单**（晨间DSA `0d1bb1811d94` / 每小时 `51814bf28ed7` / 收盘前 `91df35c579fb` / 每日分析 `6258267cf112`），且都带一句"紫光已移除不分析"之类的排他说明。改自选时必须用 `cronjob action=update` 传**完整新 prompt** 逐条改写这些句子(数字+名单+排他说明)，否则报告仍按旧名单分析。读全文用：`python3 -c "import json; [print(j['prompt']) for j in json.load(open('cron/jobs.json'))['jobs'] if j['id']=='<id>']"`。
